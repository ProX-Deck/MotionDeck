# 特效生成:SRT → Overlay JSON

把 SRT 字幕自动编排成动效卡片时间轴,输出 **overlay JSON**,用户在 MotionDeck(双击「启动 MotionDeck.command」,或运行 `npm start`)里点「📥 导入 JSON」即可预览微调。

## 开工与收工(每次会话的固定动作)

- **开工先读 STATUS.md**:在这期视频的素材目录里找 `STATUS.md`(和 SRT/JSON 同目录)。有就先读,按里面的「当前阶段」和「待办」接着干,不要求用户重新交代;没有就从同目录 `STATUS.template.md`(本 skill 目录下)复制一份创建,填上已知信息。
- **所有产物落在导入 SRT 所在目录,禁止写项目 `tmp/`**:overlay JSON、`STATUS.md` 等一律和 SRT 放在**同一目录**(技能约定「与 SRT/JSON 同目录」,且这正是用户导入 JSON 的地方,方便取用)。**不要**为某期编排在工作区另建 `tmp/xxx` 子目录。生成 JSON 直接用本对话里的编排逻辑产出,**不落任何生成脚本到技能或项目目录**(非通用脚本用完即弃,不留存)。
- **卡片库(下方【卡片库】)是参考表**:列出当前环境可用的核心卡与参考卡种;它随版本更新、由维护方重新生成。新卡接入后,在【卡片库】对应行补一句「触发条件」(什么时候用这张卡)即可。运行时实际可用卡以 available-cards.json 为准(见「卡片可见性」)。
- **卡片可见性(哪些卡可用)**:本 skill **默认只知 22 张核心卡**(`chapter-bar` `pin-board` `caption-track` `stat-proof` `ring-metric` `odometer` `rank-bars` `growth-curve` `progress-bar` `versus-card` `quote-lockup` `punch-pill` `step-timeline` `checklist` `term-card` `ui-callout` `blur-text` `type-shift` `motion-blur-slam-in` `entity-chips` `focus-card` `terminal-3d`)。其余可用卡(授权解锁的 65 张内置卡 + 云端动态卡 + 本机 `data/cards` 卡)读本机 **`MotionDeck/data/available-cards.json`**(相对本 skill 文件为 `../../MotionDeck/data/available-cards.json`)合并进卡片池。**若该相对路径读不到(用户移动了目录/改名),主动用 AskUserQuestion 或直接问用户当前 `MotionDeck/` 目录的绝对路径,用绝对路径重试读取**;切勿默默当 22 张处理,也**绝不在 skill 文件里写死域名**。
- **开工先读偏好表**:本 skill 目录下的 `我的偏好.default.md`(出厂中性默认)+ `我的偏好.md`(用户自己的,同名条目覆盖默认)。本文档里凡是写成 **【偏好·分区·条目】** 的地方,取值一律去这两份表里查,**不要自己编数字**。两份都查不到就按 default 表的说法办(多数是"不设/可选",那就真的不设)。
- **收工必更新 STATUS.md**:每次交付/修改完,把当前阶段、关键文件路径、本期决定(主色/皮肤/风格)、已完成、待办、运镜建议清单写回去。下一个会话靠它接力。

## 工作流程

1. **解析 SRT**:提取每条字幕的 start/end(秒)和文本。相邻字幕如果属于同一个语义段(同一个观点/列举/数据),合并为一个时间区间。
2. **分段脚本(先于选卡,本 skill 的核心步骤,见【先分段,再配卡】)**:把整篇稿子拆成「章 → 段 → 元素」三级:章 3-6 个(给 `chapter-bar`);**段 = 10-30s 恰好一个论点**,每段标注 起止秒/中文标题/英文小标签/语义色/段界收法;元素 = 段内的数字/截图/图表/结论行,各自标进场秒(对齐台词句)。每个论点标注证据形态(数字?截图可证?取舍?立场?量级对比?)——这决定用哪张证据卡。对**无数据纯口播/反思类**(全片无硬数字·截图·数据对比)尤其要切细:段取下限 10-15s,且每段内部必须用叙事节拍卡(见【无数据纯口播 / 反思类 vlog 怎么编】)切开,绝不允一张文字卡干挺 20s+。**是"用动画呈现语义",不是"给字幕加特效"**:卡的内容来自论点和证据,不是 SRT 原句复述。
3. **识别内容类型**:钩子设问 / 痛点罗列 / 反转金句 / 数据 / 术语解释 / 步骤流程 / 引用他人 / 对比 / 列举 / 分点 / 结尾升华……
4. **匹配卡片**:先读本 skill 目录下的 `我的偏好.md` / `我的偏好.default.md`(取值表)和 `经验规则.md`(定性偏好),和本文件规则合并;冲突时以更具体、更新的为准,再按下方【卡片库】的触发条件选卡。**只能用卡片库里的 kind,严禁发明新类型。** 若用户提供了「脚本设计」文档(每段已配好卡),以该文档为准,只补时间和缺漏。
5. **编排落位与密度**(见【编排规则】)。
6. **输出纯 JSON**(见【输出格式】)+ 分段脚本(段落表,方便用户检查段落划分)+ 素材清单(见【素材清单】),除这两者外不输出解释文字。

## lintOff 是用户的主动决定(硬规则)

卡片上的 `"lintOff": true` 或 `"lintOff": ["规则名"]` 是用户在 Studio 里亲手点「忽略」写下的标记,表示"我知道这条规则,我就是要这样"。**重新编排、单卡重写、加密时一律原样保留这个字段,严禁把这张卡"修复"成规则认可的样子。**

## 输出格式(必须严格遵守)

```json
{
  "version": 1,
  "theme": "dark",
  "cards": [
    {
      "id": "card-1",
      "kind": "blur-text",
      "start": 0.5,
      "end": 4.2,
      "params": { "text": "你是不是|也这样?", "accent": "blue", "position": "center" }
    }
  ]
}
```

- `theme`:`"dark"`(暗调视频)或 `"light"`(亮调视频)。用户没说就问一句;不方便问默认 `"dark"`。
- `id`:`card-1`、`card-2`… 递增,不得重复。
- `kind`:必须是卡片库中的 id。
- `start`/`end`:秒(可带小数),**必须来自 SRT 的真实时间**,end > start。
- `seg`(卡片顶层字段,可选):**段落分组**——同 seg 的卡进左列自动顺排容器(x=120,y=96 起竖排,间距 28px,左边线天然共线,卡高变化自动让位)。首成员(整段最先出现的那张卡)是整段的拖拽把手:它的 offsetX/offsetY 移动整段;其余成员的 offset 是组内微调。**同一段里并排陈列的卡必须同 seg**;一段跨了好几句时,后进场的卡照样并进同一个 seg(会在前面的卡下方自然接替)。独立大卡(type-shift/terminal-3d/focus-card 等一段一张的)不用 seg。
- `params`:只写需要覆盖的字段,其余自动用该卡调试好的默认值(**不要臆造字段**)。
- 通用参数(所有卡都支持):`theme`(覆盖全局)、`offsetX`/`offsetY`(位置微调 px)、`accent`(强调色,只能用这三个:`blue`(数据蓝)/`alert`(否定红)/`orange`(转变橙))、`scale`(单卡大小倍数)、`speed`(单卡动画速度倍数,默认 1)。
- **禁止**:新卡片类型、自定义 UI/样式字段(如 x/y/w/fontSize/color 十六进制)、无时间的卡、把整期内容塞进一张卡、输出 JSON 以外的内容。
- **多条目参数必须写字符串,禁止 JSON 数组**:`lines`/`items`/`steps`/`quote`/`text`/`chapters`/`evidence`/`script`/`rows`/`bars` 等所有「一条一行 / 用 `|` 或 `\n` 分隔」的参数,一律写成**单个字符串**(用 `|` 或换行分隔各条目);工作台按字符串 `split` 解析,传数组会在导入时抛 `e.split is not a function`(已踩坑:`caption-track.lines` 曾误写成数组)。

## 交付前自检(必做,且必须跑 lint 脚本)

生成 JSON 后、**交付前必须先跑本技能自带的 `lint-overlay.mjs`**——它独立移植自工作台内置 overlay 体检(lint)规则(阈值、规则、quiet-gap 算法完全一致),让技能阶段的体检和工作台导入时的体检是同一套,不再把建议漏到导入阶段。

```bash
node lint-overlay.mjs <生成的overlay.json> --duration <视频时长秒> [--main-video]
# 退出码: 有 error 级议题 => 1(必修,必须改);仅 warn => 0(warn = 违反编排规律,人判优先)
```

脚本覆盖的议题(与工作台一致):`caption-track` 提醒(常驻字幕卡必有,确认原片无烧录字幕即可)、`quiet-gap`(相邻动作点空窗>10s,密度建议)、`short-dwell`(内容卡驻留<2s)、`decimal-percent`(口播取整更顺)、`placeholder-text`(示例/占位文案残留)、`over-duration`(超视频时长)、`adjacent-kind`(相邻内容卡同 kind)。**`caption-track` 与若干 `quiet-gap` 在本工作流里基本必现**:前者是因为我们恒定加字幕层、确认无烧录字幕即可;后者是因为本工作流密度低于工作台「10–16 张/分钟」目标,属编排密度选择,人判。**时间重叠已放开,`stack-overlap`(同落位叠卡)不再作为议题——卡片时间窗可自由交叠(同时或交叉)。**

> 历史教训:本技能去源码化时曾删掉 `lint:overlay` 脚本,只留人工结构自检(类型/相邻/start<end),导致 `e.split is not a function`、quiet-gap 等全漏到导入阶段。**现在以 `lint-overlay.mjs` 补齐,交付前一律跑它。**

人工重点复核(脚本不替代的):
- **多条目参数必须是字符串,不是数组**:`caption-track.lines`(换行)、`pin-board.items`/`checklist.items`/`step-timeline.steps`/`chapter-bar.chapters`/`bar-chart-growth.bars`/`rank-bars.rows`(`|`)、`quote-lockup.quote`/`blur-text.text`/`type-shift.lines`(`|`)、`entity-chips.chips`(`\n`)等——传数组会在导入时抛 `e.split is not a function`。脚本已断言这些 key `typeof === 'string'`。
- **进入时间必须锚到字幕真实句首**:逐张卡核对——卡进入那一刻,它要讲的核心词口播是否正好说到(留 0.3~0.5s 入场余量)。段级概括卡(覆盖一整段、核心词在段中)最容易早到,需单独重锚到核心词句首。
- `accent` 只能是 `blue` / `alert` / `orange` 三选一;`start < end` 且取自 SRT 真实时间(非均分)。

## 常驻层(见【偏好·常驻层】)

全程在场的常驻层能让画面不空。**配哪几张、配不配,见【偏好·常驻层】**;要配的话各一张,start=0、end=视频结尾:

1. `chapter-bar` 章节导航条:把稿子分成若干章(章数、章名长度见【偏好·常驻层】),`chapters` 填「章名 起始秒」(| 分隔)。章节切换点选在讲述的自然转折句上。
2. `caption-track` 双语字幕层:`lines` 一行一条 `起始|结束|中文|英文`。中文从 SRT 原句轻度整理(去语气词、口误);**每条都给英文翻译**(短而地道,小字展示);每条至少标一处 `*关键词*`(这句真正的重点词,标了会被强调色点亮)。文本里不许出现竖线(用 / 代替)。**`lines` 必须是单个字符串(各条以换行 `\n` 分隔),严禁写成 JSON 数组**——工作台 `CaptionTrack` 直接对 `params.lines` 调 `raw.split(/\r?\n/)`,传数组会在导入时抛 `e.split is not a function`。


这两类常驻卡都不计入"密度/多样性"指标,也不受"相邻不同 kind"约束;其余内容卡照常编排。

## 先分段,再配卡(段落场景制,优先级最高)

整体感来自"按段组织版面":**逐句进场的是元素,按段组织的是版面**。严禁直接从 SRT 逐句挑卡——必须先做出【工作流程】第 2 步的分段脚本,再按段编排:

1. **分段脚本格式**(每段一行):`起止秒 | 中文标题 | 英文小标签 | 语义色 | 段界收法 | 元素列表(形态+进场秒)`。标题长度见【偏好·文字量】;英文小标签 = 段意的英文直译,**配不配、什么字体风格见【偏好·文字量·英文小标签】**,填进卡的 kicker/en 类字段。
2. **段落要有人立着**:没有专门的段头卡,这件事交给常驻的 `chapter-bar`——一张从 0 拉到片尾,`chapters` 参数按「章节名 起始秒」写全本期段落,讲到哪推进到哪。段落开场想再重一点,可以让 `stat-proof` 的 kicker 或一张 `type-shift` 承担立题,但不必每段都加。
3. **一段一结构(整体感的来源,最重要)**:同段的卡可填 `seg` 字段共线顺排(**用不用见【偏好·结构·seg】**)。没有专门的段头卡,**段落感由常驻的 `chapter-bar` 承担**——顶部章节导航从头到尾在场,讲到哪一段就推进到哪一格,观众永远知道现在在哪。一段的标准结构是**主卡 + 钉板**两件:段内**最多一张"标志性主卡"**承担这段的主要画面(terminal-3d/focus-card/巨字这类,一段一张);零散要点用 `pin-board` 钉在角落陪跑整段,讲过不撤。**数字和数据用专卡而不是堆文字**:一出现数字/比例/趋势,直接上 ring-metric / odometer / stat-proof 这类"动画在演语义"的卡,别用纯文字讲数字。**严禁一段叠四五张各自为政的小卡**(每张卡底板/字号/宽度都不同,offset 对得再齐也是乱的)——整体感来自 chapter-bar 的统一节奏,不来自堆卡。段内只进不出:元素踩台词进场,停到段尾。
4. **段界可交叠,不强制统一清场**:段落结束时同段卡可一起退场(共用 end),也可延续到下一段、与后续卡交叉重叠——时间窗自由交叠。换景仍可用全屏卡(`focus-card`,或用户自己导入的录屏底)整段换景。**换景频率见【偏好·结构】**,给观众喘息。
5. **一段一色**:段内所有卡 `accent` 一致 = 该段主色(色义约定见【偏好·颜色】)。
6. **来源行是证据的标配**:证据卡必须带出处(`stat-proof` 的 footZh、`pin-board` 的 subtitle、`quote-lockup` 的 author),格式仿 mono 来源行:`SOURCE·OpenAI官方·2026.6` / `NEWS·7/14·一个人手搓` / `CASE·博主自述`。没有出处的截图不算证据。
7. **双列对照排版**(GLOBAL vs CHINA 式):段意本身是左右对照(国外vs国内/旧vs新/A派vs B派)时,拆成两个同时间窗的 seg 分组——左组正常(默认落左列),右组的段头填【偏好·落位·双列对照的右列 offsetX】整组挪到人物右侧,两列各自顺排、同段同色,中缝可放一颗结论药丸(punch-pill center)。
8. **留白段**:密段之间安排"只有段头、什么都不堆"的空段(时长见【偏好·结构】)。不是每段都要厚,呼吸感来自疏密交替。

## 编排规则

- **宁多毋缺(第一原则)**:Studio 里删一张卡只要按一下 Delete,缺一张卡却要重新对时间——所以**拿不准要不要配卡的段落,一律配上**。宁可用户删掉三成,不要让用户补一张。
- **密度**:每分钟张数见【偏好·密度与节奏·密度区间】,跟着语义走——讲到新名词、新数字、新动作、新情绪、新例子就出新东西。目标是**每隔【偏好·密度与节奏·新动作间隔】有一个新动作**(新卡进场,或卡内下一条弹出;两者都算)。留白只给真正的叙述过渡,上限见【偏好·密度与节奏·留白上限】。
- **多样性(硬指标)**:
  - 相邻两张卡**不许同 kind**(常驻章节卡除外);
  - 每 60 秒内要用到的不同分组数、全片 kind 种类数下限、同种卡重复上限,**都见【偏好·多样性】**(偏好表写「不设」就真的不设,别自己补一个)。
- **同屏可以叠多张,时间上允许重叠(同时出现 / 前后交叉都行)**:
  - 每个章节可给一张**常驻章节卡**(如 `step-timeline`/`punch-pill` 放角落,整章不消失,期间其他卡来来去去);
  - 常驻卡之外再叠几张轮换内容卡(上限见【偏好·多样性·同屏叠卡】);**落位可错开(left/right/bottom/top)也可同落位,进场时间允许交叠——前一张未退、后一张已进(交叉),或两张同时出现,都不受限**,不再强制错峰或「同一落位只许一张」。
  - **不再要求「段尾全体清场」**:卡片时间窗可自由交叠,跨段也可延续;`dimAt` 让位机制照常可用(旧信息在场但压暗让位)。
  - 标注"独占全屏"的卡(focus-card)仍按原设计独占整屏(留白侧可叠内容卡),这是它的场景用法,不在此列。
- **落位避人(硬约束)**:人物在画面中间,卡不许盖脸。**有没有固定主轴、哪类内容落哪儿,见【偏好·落位】** —— 偏好表没规定的,按卡片自身建议的 position 落位,别自己发明一套。
- **时长**:各档时长见【偏好·密度与节奏】。内容卡一律跟着讲述时长走,不要套固定值。
- **节奏**:开头 0-5s 必须有一张钩子卡;
    - **时序锚定字幕(硬约束·治本)**:每张内容卡的 `start` **必须是它文案对应字幕句在 SRT 里开口说话的真实时刻**(精确到 0.1s);`end` 是这张卡自己讲完退场的时刻,**允许 ≥ 下一张卡的 `start`(时间窗可自由重叠——同时出现或前后交叉都允许)**,但仍建议尽量连续覆盖、无空窗。最后一张 `end` = 片尾时长。若一张卡概括多句,`start` 取该段**首句**时刻,`end` 取该段末句时刻。**严禁"连续平铺"(start = 上一张 end、靠分段均分时长)——那是和字幕脱节的根因,会让卡片在台词还没说时就冒出来。** `chapter-bar` 的章节时刻同样要填真实 SRT cue 时间。相邻两张锚定句间隔 < 2s(快嘴段)时,保留各自真实 `start`、给较短的卡加 `"lintOff": ["short-dwell"]` 标注刻意为之。**重叠已放开,不必为了避免重叠去拉长或挪时间,按讲述节奏自然交叠即可。** 每个"总结/反转/金句/数字"时刻都配卡。
- **让在场的卡活着(卡内逐条)**:节奏感来自"卡内容在动",不是狂加新卡。超过 8s 的卡一律选能逐条推进的:`pin-board` 逐条钉要点、`checklist` 逐项打勾、`step-timeline` 讲到哪章亮哪章、`focus-card` 要点逐条弹入。别让一张卡一次全亮然后干等。
- **一个论点养一条线索,别撒一把卡**:一个论点占住整段(时长见【偏好·密度与节奏·论点板陪跑】),信息按讲述节奏依次进场——`chapter-bar` 推进到本段立题 → 数据专卡出数字 → `pin-board` 钉住结论要点,钉过的不撤场。厚度感来自累积,不来自卡数。讲人/公司时先钉 `entity-chips` 名牌再展开;讲证据用 `stat-proof` 给数字、`quote-lockup` 给出处。

## 图形优先(重要:防 PPT 化)

动效是**视觉伴奏**,不是把字幕再打一遍。按这个优先级选卡:

1. **证据优先(最高)**:观点要用数字和真素材背书,不要用文字复述——里程碑/成绩用 `stat-proof`(滚动计数);比例/达成度用 `ring-metric`;整数规模用 `odometer`;取舍、二选一用 `versus-card`;要演示的界面让用户「导入视频」把录屏铺成底,再用 `ui-callout` 圈出要讲的那块。
2. **数字可视化**:一出现数字就用 `odometer`/`ring-metric`/`stat-proof`——大数字 + 一行小注,不写整句。
3. **图标/图形结构**:并列列举 → `pin-board`(要点逐条钉住,讲过不撤);流程/步骤 → `step-timeline`(章节大纲)或 `checklist`(逐项打勾);二选一 → `versus-card`;文件/代码/和 AI 的拉扯对话 → `terminal-3d`。
4. **实物图/截图/录屏**:引用他人的话 → `quote-lockup`(逐行揭示 + 署名);演示界面/网页/代码 → 用**运镜·相机**系列把录屏或截图当底噪运镜(`cam-push-in` 缓推聚焦 / `cam-pull-reveal` 拉远展全貌 / `cam-cursor-zoom` 怼近看清长命令 / `cam-pip-zoom` 长期挂局部特写 / `cam-orbit` 立体环绕 / `cam-tour` 长图巡游 / `cam-sway` 宽页横扫 / `cam-tilt` 立成立面);要**圈注/标注/打码/放大镜**截图上某块,用 **网页截图** 系列(`webspot-spotlight` / `webspot-loupe` / `webspot-callout` / `webspot-redact` / `webspot-cursor`)直接在截图上作图;讲界面某个区域也可叠 `ui-callout` 圈出来。聊天记录、群消息这类长文字,让用户录屏或截图铺底,绝不要打成文字卡。
5. **纯文字卡是最后的选择**:只给钩子/反转/金句时刻(`punch-pill`/`blur-text`/`type-shift`/`quote-lockup`),占比上限见【偏好·文字量】。

文字量红线:
- **禁止把 SRT 原句整句搬上卡**(硬约束),必须提炼成词块。**字数上限见【偏好·文字量】** —— 偏好表没给数字,就守住「明显短于口播原句」这条底线。
- 需要长内容时选"图"的形态(截图/封面/引用卡),不选"段落"。
- **卡内节奏必须卡点(重要)**:凡是"逐条/逐步出现"的卡(checklist、step-timeline、pin-board、focus-card、blur-text、type-shift 等),它的节奏参数(`stepMs`/`staggerMs`/`shiftAtMs`/`countMs`)**必须用 SRT 实际时长推算,不许用默认值**:
  - 计算:`节奏参数 ≈ (对应 SRT 段总时长(秒) × 1000) ÷ 条目数`,再按第一条出现所需的进场时间略减 10%。
  - 例:三个痛点分别在 15.1s / 19.1s / 24.6s 开口讲,段落到 27.9s 结束 → 每条约 (27.9−15.1)/3 ≈ 4.3s → `stepMs: 4200`。
  - 条目间隔明显不均匀时,优先把卡拆成时间不同的多张小卡,或选不分条的卡型。
  - `strikeAtMs`(反转时刻)= 转折句在 SRT 里开口的时间 − 卡片 start,换算成毫秒。
- **颜色分工**:同一期里同一语义永远同色,这是硬要求。**但「哪个色代表哪种语义」是设计约定,见【偏好·颜色·色义约定】** —— 偏好表没规定就整期用同一个 accent,千万别每张卡一个色。

## 运镜·相机 与 网页截图 两族卡的设计意图

工作台新增卡里有一批**运镜·相机 8 张、网页截图 5 张**,以及 **countdown-arc-scatter / glass-code-walk / pencil-sketch-draw / bed-echo-blur / flying-words** 等 HUD 卡。它们与正文文字卡不是一个层——是"把真实素材(截图 / 录屏)当底噪做运镜"的层,选用时遵循下面几条,避免和纯文字卡混用导致降级:

- 这些卡都是**编译进包、由工作台实时驱动的 HTML/CSS 运行时卡**:运动用 `useProgress` / `useElapsed` 等钩子驱动,CSS 关键帧 + transform 表达;成片由工作台导出(透明 MOV 等)。因此要"还原"的是**运动语义 + 关键参数对齐**(焦距 / 弧角 / 缓动 / 层级 / 落位),不是像素级外观复制。
- **相机极缓推拉 = 镜头的"生命"**:`cam-*` 八张把截图 / 录屏当底噪做极缓推进 / 拉出,让画面"永远在动"。这是"让画面活着"的手段——**只在有真实截图 / 录屏要推拉时用**;没有 `src` 素材时该卡只会渲染灰块占位,等于降级成空卡,宁可不塞。

选用原则(与本项目通用规则一致,直接套用):

1. **证据优先 / 素材必需**:观点用真数字、真截图背书,不堆文字卡 —— 见【图形优先】第 1 条。
2. **先分段,再配卡**:按语义段落切,新元素只在语义拍边界进场,禁止"一句一个新元素" —— 见【先分段,再配卡】。
3. **相机极缓推拉**:`cam-*` 系列 = 极缓运镜让画面活着,只在有真实素材要推拉时用;无 `src` 素材就别塞。
4. **网页要"拍"不是"贴"**:网页证据用"滚 / 巡 / 放大 / 划"四法,对应 **网页截图** 系列 + **放大镜聚焦** 组(`magnifier-detail` / `scanline-annotate` / `focus-card`)。
5. **开镜不空台 / 一个节拍一个主角**:开场到第一个动效锚点之间必须有承载画面;同屏同一时刻只一个重音 —— 见【落位避人】【让在场的卡活着】。

落地时仍以本 skill 的分段脚本、图形优先、编排规则为准;上面几条只是帮你判断**什么时候该选运镜 / 截图这两族卡**。

## 无数据纯口播 / 反思类 vlog 怎么编(最容易编稀的地方)

这类稿子全片没有硬数字、截图、数据对比,只有叙事 + 论点 + 情绪。技能默认容易犯两个错:**(1) 分段太粗**——把 100+s 切成 3-4 段、每段一张文字卡干挺 20s+;(2) **只复用 `blur-text`/`type-shift`/`quote-lockup`/`punch-pill` 几种文字卡**,把"图形优先"抛到脑后。

**硬纪律(默认生效,偏好表未覆盖时强制执行;达不到就回头把文字卡换成上方【免素材丰富卡型速查】里的对应卡型):**
- **纯文字卡定义**:仅 `blur-text` / `punch-pill` / `quote-lockup` / `type-shift` 这四种算"纯文字卡";`impact-open-title`/`strike-and-replace`/`keyword-pop-highlight`/`slab-punch-title`/`per-character-rise`/`outline-box-title`/`versus-card`/`step-timeline`/`stat-proof`/`terminal-3d` 等带图形/动效主体的**不算**纯文字卡。
- **占比红线**:纯文字卡数量 ≤ 全片内容卡总数的 **50%**(偏好表写了更低下限的从其下限)。
- **连续红线**:**禁止连续 3 张及以上纯文字卡相邻**(相邻同段或跨段都算);要连排也必须在中间插一张图形/证据类卡隔开。
- **每段至少 1 张图形/证据卡**:每个语义段至少用一张上表里的非纯文字卡型承担主画面,不能整段靠文字卡干挺。

正确打法:

- **分段取下限**:段 = 10-15s 一个论点(别放任到 30s),100+s 的口播至少切 8-12 段。
- **叙事节拍卡才是主力**(都在 58 卡库里,不是纯文字卡):讲到一个关键词就 `keyword-pop-highlight` 砸出来;转折/金句用 `slab-punch-title`/`speed-slab-title`;要圈重点用 `ink-underline`/`highlighter-sweep`;立题用 `outline-box-title`;收尾一句用 `per-character-rise` 逐字顶上来;进入新段落用 `chapter-title-card`/`color-slam-beat-card` 硬切换景;提到 AI/工具时让 `terminal-3d` 自演一段"问→答"。
- **目标是每 5-8s 一个新视觉动作**(新卡进场,或卡内下一条弹出),而不是一张卡撑一段。宁多毋缺——用户删三成比补一张容易。

## 通用参数(所有卡都支持)

- `dimAt`(秒,时间轴绝对时间):**讲过变浅+缩小**。到点后整卡压暗并缩小(幅度见【偏好·让位与压暗】,偏好表没给就用组件默认值),同 seg 顺排的卡缩放时(zoom 参与布局,下方内容自动上移补位,不会被挤出屏幕),但不退场;整个话题结束才用 `end` 退场。`dimMode` 可选让位方式:`both`(默认,变浅+缩小)/`fade`(只变浅)/`shrink`(只缩小),一般不用填。编排时给每张证据/论点卡都填:值 = 下一个话题开始的秒数。这是"组合感"的关键——旧信息在场但让位,观众随时能回看已讲过的论据。

## 可用卡全量清单(权威来源)

本机 `MotionDeck/data/available-cards.json` 是**工作台每次启动重写**的单一真相:列出当前环境所有可用卡(`source` 标 `core`/`online`/`local`,`spec` 用相对路径、**不含域名**)。编排前先读它拿到核心卡之外的可用卡,再与上方【卡片库】合并。读不到就按「开工」规则问用户目录路径。**skill 文件本身不写域名、不写绝对地址。**
- `source` 字段含义:`core`=22 张核心(本文件已知);`online`=云端授权后解锁的其余内置卡 + 云端动态卡(两类同款展示,用法见上方【卡片库】,此文件只标可用性;云端动态卡额外带 `spec` 相对路径);`local`=本机 `data/cards/` 卡(**不在**【卡片库】表里,条目额外带 `description` 和 `params`(参数摘要:key/label/type/options/default),照着填参即可);`spec` 为相对路径,**不含域名**。

## 指定卡片(用户点单,优先级最高)

用户可以在给 SRT 的同时**指定某段话用某张卡**,支持三种写法(可混用、可一次点多单):

- **按原话**:「"收藏了不等于学习了"这句用 versus-card」→ 在 SRT 里全文检索这句话(允许近似匹配),用它所在字幕条的真实起止时间。
- **按时间**:「2:10-2:25 用 versus-card」→ 直接用给定区间(换算成秒)。
- **按内容描述**:「讲三个痛点那段用 pin-board」「演示 Obsidian 那段铺录屏底 + `ui-callout` 圈注」→ 先在 SRT 里定位该语义段,再套卡。

处理规则:
1. **点单必须服从**:指定的段落用指定的 kind,即使【图形优先】会选别的卡;其余没点单的段落照常自动编排。
2. 内容仍要按该卡的形态**重新提炼**(词块/条目/节奏参数照【卡内节奏必须卡点】用 SRT 推算),不是把原话搬上去。
3. 点单的卡与自动编排的卡冲突时(与独占全屏卡 focus-card 重叠),**挪自动卡,不动点单卡**。
4. 指定的 kind 不在卡片库里时,不要硬造:回复一句说明,并推荐 1-2 个最接近的卡让用户选。
5. 找不到指定的那句话/那个时间段时,先问,不要猜。

## 加密(只增不改)

当用户给出**已调好的 overlay JSON + SRT** 并要求「加密/再丰盛一点/多出些卡」时:

1. **已有的卡一张不动**(id/时间/参数原样保留)——那是用户手调过的。
2. 只在**空隙和薄弱段**插入新卡:先扫出 >3s 没有新动作的时间段,按【编排规则】的密度和多样性往里补。
3. 新卡 id 从现有最大编号继续递增,不与旧卡同落位同时刻,不紧邻同 kind。
4. 输出整份 JSON(旧卡 + 新卡,按 start 排序),并附一句:新增了几张、集中在哪些时间段。

## 单卡重写(换卡)

当用户给出**已有的 overlay JSON** 并要求「把 card-X 换成 <kind>」时:

1. 只动那一张卡:`id`、`start`、`end` 原样保留;`theme`/`accent`/`offsetX`/`offsetY`/`scale`/`speed` 尽量沿用。
2. **内容必须重写,不是搬字**:回到 SRT 里该卡时间段(start–end)的原话,按新 kind 的形态重新组织(条目数、格式、节奏参数都按新卡该有的样子来,节奏仍按【卡内节奏必须卡点】规则用 SRT 推算)。
3. 其他卡一律不动,输出**整份 JSON**。
4. 没给 SRT 时先要 SRT;实在没有,就基于旧卡文字改写,但要说明是降级处理。

## 学一下(从用户的修改沉淀个人偏好)

**不自动跑**。用户在 Studio 导出后说「学一下」才执行。
**这是用户长出自己风格的唯一通道** —— 出厂的 `我的偏好.default.md` 是中性的,
不跑这一步,他每期都在用别人的取值。用户第一次导出时 Studio 会提示他这件事,
但如果他问起「怎么让它更像我的风格」,答案就是这一节。

执行步骤:

1. **拿素材**:读 `../../MotionDeck/output/logs/` 里**最新**的 `*-review-log.json`(落盘目录名是 `logs`,不是 `review-logs`——Studio 每次在「编辑台」整条导出 JSON/MOV 时自动 POST `/api/review-log` 落盘,单卡预览导出不落),含 `origin`(AI 初选编排)和 `final`(用户调完的终选)。用户也可以直接丢两份 JSON。
2. **逐卡 diff**,归类:被删的卡 / 新增的卡 / 换了 kind 的卡 / 挪了时间的卡 / 改了参数的卡(位置/大小/节奏/文字/颜色)。
3. **抽象可泛化的偏好**,不记流水账:同类修改出现 ≥2 次才算倾向;只出现一次的,先问是不是巧合。对比"AI 为何这么编 vs用户为何这么改"。
4. **逐条确认**:这是**正当例外**(这期特殊,不学)还是**改规则**(以后都这样)?只写"已确认"的。
5. 确认的结论**按性质分两个文件写**,每条都带出处 `(学于 <视频名> YYYY-MM-DD;已确认)`:
   - **能填进取值表的**(密度几张/分钟、字数上限、落位主轴、色义映射、时长档、开关要不要开……)
     → 写进本 skill 目录 **`我的偏好.md`**,对应 `我的偏好.default.md` 里的同名条目。
     没有 `我的偏好.md` 就照 default 表的分区结构新建一份。**不要改 `我的偏好.default.md`**(升级会覆盖)。
   - **只能用一句话说清的定性规则**(哪类卡降权、什么情况下换什么打法、他为什么这么改)
     → 写进本 skill 目录 **`经验规则.md`**。
   与既有条目冲突时,提醒用户二选一,别两条都留着。
   机器可判的阈值(驻留秒数、scale 档位、空白间隔、底板叠层、块级标题落位)若工作台支持,
   可同步进对应的本地规则文件,让校验也跟着他的标准走。
6. 写完提醒:如果你在多个 Agent 里都装了这个 skill,记得同步过去。

## 素材清单(交付时必附)

凡编排里有**真正需要用户补素材**的位(`img1` 图、`videoSrc` 录屏、`src` 视频/图),交付 JSON 时**必须附一份素材清单**:每张卡一行,写「卡 id · 时间 · 需要用户补什么录屏/截图(具体到'B站后台涨粉曲线'这种程度)」。没有素材清单的编排,这些卡会空着上片。

`focus-card` 的 `camSrc` **不算**:它留空时导出会自动用导入的口播原片,不需要用户补任何东西,别把它写进素材清单。

## 截图 / 图片素材怎么来(webspot* / cam* 等需要 `src` 的卡)

**网页截图类**(`webspot-spotlight` / `webspot-loupe` / `webspot-callout` / `webspot-redact` / `webspot-cursor`)和**运镜·相机类**(`cam-*` 八张)的 `src` 都是一张网页/界面/图片截图,**工作台的「网页截图」自动采集按钮已移除**,截图只能从两条路来:

1. **用户提供**:选卡阶段直接问用户「这张网页截图卡需要一张对应截图,请把图片给我(或你本地导入 JSON 后在参数面板点『选择截图』上传)」。
2. **授权 agent 自动截图**:若用户明确授权,agent 用自己的浏览器/截图工具(如 Playwright / agent-browser)把目标页截好,**存成 PNG 放进 `MotionDeck/output/src/video/`**,再把文件名写进 JSON。

无论哪条路,JSON 里 `src` 必须是**可被工作台服务器直接服务的 URL**,格式固定为 **`/demo/<文件名>.png`**(文件实际落在 `output/src/video/<文件名>.png`;用户走参数面板「选择截图」上传时返回的也是这个 `/demo/...` 路径)。**不要写物理相对路径**(如 `output/src/video/xxx.png`)——运行时只认 `/demo/` 服务地址,物理路径预览/导出都读不出图。

> 选卡阶段的落地动作:凡本片用了 `src` 类卡,在【素材清单】里逐张列出「卡 id · 时间 · 需要哪张截图(具体到一个页面/区域)」;用户给了图就走上传、授权了就让 agent 截图落盘,两者都保证 JSON 的 `src` 最终是 `/demo/<文件名>.png`。

## 交付方式

生成后把 JSON 存为 `<视频名>-overlay.json`,**放在导入 SRT 的同一目录下**交给用户(不要写项目 `tmp/`),并提示:「在 MotionDeck 点 📥 导入 JSON 预览,点卡片可微调参数,改完 📤 导出保存」。
